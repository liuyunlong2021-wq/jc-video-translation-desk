# Gemini 3.6 Flash 真实能力与受控工作流

> 状态：基于现有代码、测试、设计文档与既有多模态排查整理；真实付费样片基准仍待执行
>
> 更新：2026-08-06
>
> 用途：供视频翻译、字幕识别、说话人判断、视频反推和提示词反推工作流设计使用

## 先看结论

`gemini-3.6-flash` 在本项目中应被定位为**原生视频理解器和歧义裁决器**，不是字幕流水线的唯一事实源。

它最有价值的能力不是替代 Faster-Whisper，而是同时看到画面、听到声音、读取字幕候选和项目上下文后，补充以下证据：谁在说话、角色在做什么、语气与关系是什么、画面文字是什么、Whisper 哪些词可能听错、某句翻译在当前剧情里应取哪个含义。

正确主链是：

```text
ffprobe 获取媒体事实
  -> Faster-Whisper 建立不可变 cue 与母时间轴
  -> Gemini 全片理解人物、场景、关系和术语
  -> Gemini 在 cue 时间窗内补充视觉/听觉证据
  -> 程序找出冲突
  -> 只对冲突片段再次裁决
  -> 确认源字幕
  -> 带上下文翻译
  -> 程序做结构与语义检查
  -> 人只复核仍有冲突的项目
  -> FFmpeg 执行最终媒体处理
```

不要把“看视频、逐字转录、认人、翻译、校时、直接发布”合并成一次模型调用。已经验证可复用的设计原则是：

```text
感知 Perception -> 结构化证据 Evidence -> 确定性编译 Compilation
```

## 一、先澄清模型身份

### 已确认事实

- `gemini-3.6-flash` 是当前项目通过韭菜盒子 NewAPI/OpenAI 兼容接口调用的模型 ID。
- 项目代码确实把这个 ID 用于结构化文稿、逐镜视频分析、说话人识别和字幕翻译。
- 当前仓库的自动测试验证了请求结构、JSON 解析、cue ID 保持、数量校验和异常拒绝等程序合同。

### 尚未确认

- 现有证据不能证明 `gemini-3.6-flash` 是 Google 官方公开文档中的正式型号名称，也不能证明网关背后的上游模型版本长期不变。
- 没有可信证据支持给它写官方准确率、榜单分数、固定上下文长度、价格或速度。
- 当前项目 TDD 明确记录：真实付费 Gemini 样片调用和完整端到端验收尚未执行。

因此本文描述的是**这个项目入口在现有工作流中的实用能力边界**，不是 Google 官方模型卡。正式批量生产前，必须用同一 API Key、同一模型 ID、同一请求格式做能力预检和固定样片回归。

## 二、真实能力分级

下表的“强、中、弱”是工程定位，不是未经实测的准确率声明。

| 能力 | 工程判断 | 适合承担的工作 | 不能直接当成什么 |
|---|---|---|---|
| 原生视频场景理解 | 强 | 人物、动作、表情、互动、镜头内容、场景变化 | 帧级时间轴真值 |
| 画面 OCR 与视觉文字理解 | 强 | 招牌、聊天框、标题、画内字幕候选 | 口语转录结果 |
| 局部说话人/角色推断 | 强到中 | 结合画面、cue 窗口和已知角色判断 speaker | 长视频稳定声纹识别 |
| 全局剧情和人物关系 | 强 | 剧情摘要、角色关系、称谓、术语表、语气背景 | 未给角色库时的正式角色身份 |
| 严格结构化 JSON | 强，但必须校验 | 按 schema 返回 cue 证据、补丁和问题列表 | 天然保证永不漏项/改 ID |
| 局部歧义裁决 | 强 | 对 Whisper/Gemini 冲突片段二次判断 | 一次调用覆盖全部错误 |
| 独立听写对白 | 中 | 提供第二路 transcript 候选、纠错建议 | 唯一 ASR 和逐字真值 |
| 情绪和语气识别 | 中 | 中性、愤怒、迟疑、讽刺等制作提示 | 精密、稳定的心理标签 |
| 可见说话/画外音判断 | 中 | 判断嘴型可见、旁白、画外对白候选 | 无复核的最终 diarization |
| 场景/镜头边界 | 中 | 粗粒度场景地图、片段摘要 | 精确剪辑点 |
| 上下文翻译 | 中到强 | 结合剧情、角色、术语和前后句生成译文草稿 | 无校验可直接发布的终稿 |
| 粗粒度时间理解 | 中 | 判断动作发生在 cue 前后、寻找大致片段 | 帧准确入点/出点 |
| 音乐、重叠对白、口音下的 ASR | 弱或不稳定 | 标记疑点并给候选 | 替代专用 ASR |
| 长视频跨段说话人一致性 | 弱或不稳定 | 在全局人物表约束下辅助判断 | 稳定声纹聚类器 |
| 精确人名、术语和数字听写 | 弱到中 | 结合词表给候选 | 未提供词表时的事实源 |
| 长片一次性翻译一致性 | 弱或不稳定 | 生成首稿 | 角色口吻和术语永远统一 |
| 自报 confidence | 仅作排序信号 | 决定优先复核项 | 校准后的真实概率 |

## 三、它真正擅长什么

### 1. 把多路信息放在同一个语境里理解

专用 ASR 主要听声音；Gemini 的价值是能把声音、人物是否开口、动作、表情、画面文字、前后剧情和已有角色资料同时放进判断。比如同一句“你来了”，仅靠音频很难知道是欢迎、惊讶还是质问；视频和上下文能帮助确定语气、说话人和翻译措辞。

### 2. 给出可审计的结构化证据

模型不应只返回一份“看起来完整”的最终字幕，而应按固定 cue 返回独立字段：

```json
{
  "cueId": "cue-000123",
  "heardText": "模型独立听到的文本候选",
  "speakerCandidate": "role-002",
  "speakerEvidence": "画面中该角色口型与声音同步",
  "speechMode": "visible | offscreen | voiceover | overlapping | uncertain",
  "emotion": "neutral | happy | angry | sad | fearful | surprised | uncertain",
  "visibleAction": "角色回头并停顿",
  "ocrText": ["画面文字，必须与对白分开"],
  "issues": ["proper_noun_uncertain"],
  "confidence": 0.72
}
```

这里的 `confidence` 只用于排序，不能当成真实准确率。真正的可信度来自：证据是否完整、两路结果是否一致、程序规则是否通过、复核后是否确认。

### 3. 处理局部冲突

模型最值得花调用成本的地方，是已经知道“哪里可能错”之后，只带目标 cue、前后若干 cue、对应原片和全局人物/术语摘要，让它解决具体冲突。相比整片反复重跑，这样更快、更便宜，也更容易追责。

### 4. 为翻译补足角色和剧情上下文

翻译不能只看孤立句子。模型应收到已确认源文、角色、关系、场景、语气、术语表和相邻句。含义仍不明确时，再附原生视频片段。它适合生成上下文化译文草稿，但程序和人仍需检查否定、数字、专名、称谓和语气是否被改坏。

## 四、它不应该独自负责什么

以下边界属于架构硬约束：

- 不得静默修改 Faster-Whisper 的 cue ID、开始时间和结束时间。
- 不得自行增加、删除、拆分、合并或重排 cue。
- 不得把 OCR 看到的画面文字混入口语字幕。
- 不得在没有已确认角色库时创建正式角色；只能提出 `unknown` 或新角色候选。
- 不得直接把自报置信度当成自动通过依据。
- 不得一次生成最终 Markdown、最终 SRT 或最终剪辑时间轴并绕过程序编译。
- 不得把“结构合法”误当成“语义正确”。
- 不得把长视频一次调用的角色一致性当作声纹系统。
- 不得直接发布源字幕或译文；只能输出草稿、证据或受限补丁。

## 五、当前视频翻译实现的真实情况

### 已实现链路

当前界面流程是：

```text
Faster-Whisper 生成 cues
  -> 小于等于 20 MiB 原片原样提交；超出时由 FFmpeg 生成不超过 20 MiB 的分析副本
  -> 校准模型第一轮完整观看视频，建立全片上下文
  -> 校准模型第二轮结合全片上下文、视频时间窗和 cues，生成校准字幕与说话人草稿
  -> Gemini 只读取字幕文本和项目 Markdown，翻译全部字幕
  -> 用户后续确认
```

`identifyVideoTranslationSpeakers()` 已采用两轮多模态校准；小视频不转码，超限视频只生成分析副本，原片保留给预览、配音、混音和烧录。未知或新角色仍留给人工确认。

`translateVideoSubtitles()` 当前只发送字幕文字和项目 Markdown 上下文，**没有发送原视频或音频**。它只检查：

- 返回 cue 数量必须一致；
- cue ID 必须一致；
- 译文不能为空。

结构不合法时会重试，但目前没有语义回译、歧义检测、专名检查、否定/数字检查或针对性视频片段复核。

### 根因判断

所以当前翻译可能出现一种很隐蔽的问题：JSON 完全合法、每个 cue 都在、文本也不为空，但句意仍然翻错。根因不是简单的“模型不够强”，而是翻译调用缺少原片证据、已确认源字幕、角色语气和明确的语义验收门禁。

### 接口风险

当前说话人识别使用 OpenAI 兼容的 `file + file_data` 形式提交视频，而仓库其他调用还出现过 `video_url` 形式。哪个格式在当前网关上真的支持原生视频、是否被降级、大小和时长上限如何，必须通过真实预检确认，不能仅凭请求成功推断模型确实看到了视频。

## 六、推荐的受控工作流

### 第 0 步：能力预检

正式付费批处理前，用一个 20 至 60 秒固定样片检查：

- 同一请求能否同时提交视频、文本和 JSON schema；
- 模型能否准确复述画面中的人物、动作和一条可见文字；
- 模型能否返回全部固定 cue ID；
- 网关是否真的传递视频，而不是只处理文本；
- 重复运行三次时，结构和核心判断是否可接受；
- 请求大小、时长、耗时、费用和错误码是什么。

预检失败时应立即停止批量任务，不要退化成“模型没看视频但仍继续翻译”。

### 第 1 步：媒体探测与指纹

由 `ffprobe` 提供时长、编解码、分辨率、帧率和音轨等媒体事实，并对原片建立稳定指纹。模型不能覆盖这些事实。

### 第 2 步：Faster-Whisper 建立母时间轴

Faster-Whisper 是默认唯一 cue 和时间锚点，输出稳定 `cueId/startMs/endMs/text`。后续任何模型结果都必须引用这些 ID，只能提出文本补丁或问题，不能直接改变时间结构。

### 第 3 步：Gemini 全片理解

当请求大小和网关稳定性允许时，先做一次全片级分析，只建立全局上下文：

- 人物/角色候选及其视觉特征；
- 场景和剧情段落地图；
- 人物关系与称谓；
- 源语言、方言、语气和内容类型；
- 专名、品牌、地点、数字格式和固定译法候选；
- 画外音、旁白、重叠对白等全局风险。

这一步不生成最终字幕。

### 第 4 步：按 cue 时间窗提取多模态证据

在每个 cue 的时间窗内，Gemini 返回独立听写候选、speaker、speech mode、情绪、动作、表情和 OCR。所有字段都必须引用现有 cue ID，OCR 与 heard text 分栏保存。

### 第 5 步：程序找冲突

确定性程序至少标记：

- Whisper 与 Gemini 文本差异过大；
- 专名、数字、否定词或称谓不一致；
- 同一声音/角色在相邻 cue 中频繁跳变；
- 模型标记画外音、多人重叠或不确定；
- OCR 疑似被误认为对白；
- cue 时长与文本长度明显不匹配；
- 返回缺失、重复、越界、改 ID 或 schema 不合法。

程序只负责发现冲突，不应凭字符串相似度擅自改写对白。

### 第 6 步：只复核冲突片段

对每个冲突项裁出带少量前后余量的原生视频片段，并同时提供：Whisper 候选、Gemini 首轮候选、前后 cue、角色表、术语表和具体问题。要求模型只返回允许字段的补丁及理由。

如果两路仍冲突，进入人工复核，不得用第三次全片调用掩盖问题。

### 第 7 步：确认源字幕

源字幕确认后冻结为独立版本。任何后续翻译、配音或烧录只能消费这个已确认版本，不能回读尚未确认的 Whisper/Gemini 草稿。

### 第 8 步：上下文化翻译

翻译请求应包含：

- 已确认的源字幕；
- cue ID 和目标语言；
- 角色、人物关系、性别/称谓和语气；
- 已确认术语表与禁止改写项；
- 前后相邻 cue；
- 全集摘要和当前场景摘要；
- 配音时需要遵守的长度约束。

正常 cue 不必重复上传视频；只有多义、反讽、画外音、动作决定含义或首轮检查失败的 cue，才附对应原生片段做二次翻译。

### 第 9 步：翻译语义校验

结构校验继续保留，并增加以下检查：

- 是否遗漏或新增信息；
- 否定关系是否保持；
- 人名、地名、品牌、数字、单位是否保持；
- 说话对象、称谓、性别和人物关系是否正确；
- 语气与角色身份是否一致；
- cue 是否缺失、重复、为空或改 ID；
- 译文长度是否超过字幕阅读和目标配音上限。

语义检查可以由第二次受限模型调用提出问题，但最终通过条件必须由程序合同和人工复核共同决定，不能让模型自己给自己的答案盖章。

### 第 10 步：人工只看 unresolved 项

人工工作台不要要求用户从头审完整片，而应集中显示：原片窗口、源 cue、两路候选、冲突原因、角色/术语证据、译文和修改框。确认后记录操作者、时间和版本。

### 第 11 步：冻结产物并交给下游

确认后的源字幕和译文形成不可变版本。TTS、口型、字幕排版、烧录和 FFmpeg 只消费确认版本。上游任何修改都应显式使对应下游产物失效。

## 七、长视频与分块方式

- 能稳定提交全片时，全片只用于建立人物、关系、场景和术语等全局摘要。
- 视频过大时，只在 Whisper cue 之间的自然空隙切块，不能切断一个 cue。
- 每块保留原片绝对时间，不把块内时间当成新时间轴。
- 每块都携带同一份全局人物表、术语表、剧情摘要和上一块末尾上下文。
- 当前另一套实现曾采用约 60 秒分块，并在源文件约 80 MiB 以上时分块；这只是已有工程经验，不是模型官方上限。
- 当前模型分析输入上限按 20 MiB 产品节点执行；小于等于该值的原片不转码，超出后生成约 19 MiB 的分析副本。仍无法压入上限时进入分块流程。
- 分块结束后必须做跨块角色、术语和上下文一致性检查。

## 八、角色识别的正确设计

角色识别要区分三个概念：

| 概念 | 含义 | 处理方式 |
|---|---|---|
| visible person | 画面里出现的人 | Gemini 可直接描述和匹配视觉角色 |
| current speaker | 当前 cue 的发声者 | 综合口型、声音、前后对话和角色资料推断 |
| formal role | 项目中的正式角色 ID | 只能匹配已确认角色库，不能由模型静默创建 |

推荐输出 `speakerId | unknown`、候选列表、证据和问题类型。旁白、画外音、电话音、回忆声音、多人重叠必须有独立状态，不能为了填满字段强行归给画面中的某个人。

Gemini 不是声纹数据库。需要跨多集稳定认声时，应保存已确认角色资料和代表片段，并让模型在受限候选中匹配；如果产品未来要求法证级或大规模 diarization，再单独评估专用说话人模型。

## 九、提示词和输出合同

### 提示词应做的事

- 明确本次只负责一种任务，例如“提供 cue 证据”或“翻译确认文本”。
- 提供固定角色、术语、cue ID 和允许值。
- 要求引用画面/声音/上下文证据，不允许无依据补全。
- 不确定时返回 `unknown/uncertain`，不得猜测正式角色或台词。
- 明确 OCR 与 spoken text 分离。
- 明确只能返回 JSON，且只能修改允许字段。

### 程序必须做的事

- 使用结构化解析器和 schema，不用正则拼 JSON。
- 校验 cue 数量、ID、顺序、唯一性、非空、时间范围和枚举值。
- 校验补丁只能作用于现有 cue 和白名单字段。
- 保存原始模型响应、解析结果、模型 ID、请求指纹和版本。
- 任何非法输出整体拒绝，不做“尽量猜出模型想表达什么”的宽松修复。
- 同一输入重试时保留调用记录，避免悄悄覆盖先前证据。

## 十、最低验收基准

在宣布“Gemini 3.6 Flash 已适配视频翻译”之前，至少准备一组人工金标准样片，覆盖：

- 单人正面清晰对白；
- 双人交替对白；
- 画外音或旁白；
- 音乐压人声；
- 多人重叠对白；
- 专名、品牌、数字和否定句；
- 画面有字幕/招牌但没有对应口语；
- 翻译依赖动作、表情或上下文的句子；
- 接近或超过上传大小门限的长片。

记录并对比：

- Whisper 原始文本；
- Gemini 独立候选；
- 融合后的确认文本；
- speaker 准确情况；
- 翻译错误类型；
- cue 保持率和 schema 失败率；
- 单分钟耗时、费用、重试率；
- 同一样片重复三次的稳定性。

在这组真实数据完成前，只能说“合同和模拟测试已通过”，不能说“真实字幕、说话人和翻译准确率已验证”。

## 十一、建议实施顺序

为了最快解决当前翻译问题，按以下顺序改：

1. 先固定并确认 Faster-Whisper 源字幕，翻译不再消费未确认草稿。
2. 翻译请求增加角色、关系、术语、场景摘要和相邻 cue。
3. 增加否定、数字、专名、称谓和长度检查，异常 cue 进入复核队列。
4. 只给异常或多义 cue 附原生视频片段二次翻译。
5. 再补全片级人物/场景/术语分析和 cue 级多模态冲突裁决。
6. 最后用固定真实样片建立回归基准，再决定是否扩大自动通过范围。

不要第一步就重写整套 ASR，也不要把全部 cue 每次都带整片重跑。当前最直接的缺口是**翻译缺少确认源文和多模态语境，也缺少语义验收**。

## 十二、已确认、工程判断与待验证清单

### 已确认

- 项目使用 `gemini-3.6-flash` 这个网关模型 ID。
- 当前说话人识别会提交视频、cue、角色和项目上下文。
- 翻译文本请求提交已确认源字幕和项目 Markdown；字幕与角色校准请求提交视频分析输入、Whisper cue 和项目上下文。
- 当前校准会校验两轮结果、cue 数量、ID、唯一性和非空校准正文。
- 当前模型分析输入按 20 MiB 产品节点自适应处理。
- 程序已有结构解析和非法模型输出拒绝能力。
- 现有反推工作流支持“先感知事实，再结构化编译”的设计结论。

### 工程判断

- Gemini 应做多模态证据和歧义裁决，Whisper 应保留 cue/时间锚点。
- 翻译错误的主要架构诱因是上下文与语义门禁不足，不只是模型能力问题。
- 分层调用、冲突复核和确定性编译比一次性全自动提示词更可靠。
- 视频只应在全局理解和歧义 cue 中使用，避免不必要的成本和延迟。

### 待真实验证

- 当前网关背后的确切 Google 上游型号与版本稳定性。
- `file_data` 视频请求是否被完整转交给原生多模态模型。
- 固定样片上的听写、speaker、翻译、OCR 和长视频一致性。
- 真实大小/时长限制、延迟、费用、并发和错误率。
- 重复调用的稳定性以及 confidence 与实际正确率的关系。
