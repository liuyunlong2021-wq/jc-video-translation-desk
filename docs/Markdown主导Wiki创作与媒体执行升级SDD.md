# Markdown 主导 Wiki 创作与媒体执行升级 SDD

> 日期：2026-07-31
> 状态：待实施
> 目标版本：2.6
> 适用范围：短视频工厂桌面 App
> 参考实现：`/Users/by3/Documents/jiucaihezi-app/docs/wiki/开发/通用记忆工作台稳定性修复与Markdown体验升级SDD.md`
> 关联文档：`docs/资产图工作区与Markdown双链创作图谱升级SDD.md`
> 重要边界：只参考并适配通用记忆工作台的 Markdown 能力，不修改 `jiucaihezi-app` 的任何文件

## 1. 一句话目标

把短视频项目从“一次性生成结构化 JSON 的任务”升级为“模型读写项目 Wiki Markdown、用户直接阅读和编辑、App 从 Markdown 派生媒体任务”的创作系统。

Markdown 是用户可读、可编辑、可由 Obsidian/VS Code 打开的项目真源；`state.json` 只负责执行恢复、任务状态和精确失效；模型不再被要求一次性输出长嵌套 JSON。

## 2. 为什么停止让模型直接生成长 JSON

JSON 不是生图模型或生视频模型的输入要求。媒体模型真正需要的是提示词、参考图、比例、时长和模型参数。

当前长 JSON 的问题是：

1. 导演 Skill 一次输出几十个镜头和资产，格式错误会使整轮结果失效；
2. 用户无法直接阅读和局部修改生成结果；
3. 镜头、资产、提示词和媒体结果之间的引用关系不自然；
4. JSON 内容与项目 Wiki 之间还需要额外转换；
5. 模型承担了 App 内部执行状态的格式责任。

因此，JSON 不再是模型输出合同。必要的结构化信息由固定 Markdown 字段和 Frontmatter 表达，App 读取后在内存中组织执行队列。

## 3. 设计决断

1. 每个项目仍然是一个固定 Wiki 包，沿用现有 `projectId` 和项目目录。
2. `.raw/` 保存用户实际提交的原始材料，不由模型改写。
3. `wiki/` 保存文稿、声音、导演方案、分镜、资产、分镜图、视频和成片文档。
4. 模型拥有受控的 `read`、`grep`、`write`、`edit` 能力，只能操作当前项目目录。
5. Skill 是专业方法说明；是否读 Wiki、读哪些文件、何时写入，由模型根据任务决定。
6. App 负责工具边界、路径安全、版本检查、审批、真实执行和错误回传。
7. 阅读模式渲染 Markdown；编辑模式显示 Markdown 原文；保存后重新渲染。
8. `[[相对路径]]` 是项目内正向链接；反向链接按需扫描 Markdown，不建第二套索引数据库。
9. 资产和镜头使用稳定 `entityId`，双链只负责用户导航，不替代执行状态。
10. 图片、视频和音频生成结果完成后，由 App 将相对路径、状态和参数回写对应 Markdown。
11. 不新增数据库、不新增会话系统、不修改 `jiucaihezi-app`，不把记忆工作台的业务代码整体搬入本项目。

## 4. Wiki 文件合同

### 4.1 固定目录

沿用现有项目骨架：

```text
<projectId>/
├── .raw/
├── wiki/
│   ├── index.md
│   ├── 项目.md
│   ├── 来源索引.md
│   ├── hot.md
│   ├── log.md
│   ├── 文稿/确认文稿.md
│   ├── 声音/配音设计.md
│   ├── 分镜/导演总览.md
│   ├── 分镜/镜头/<shotId>.md
│   ├── 资产/产品/<assetId>.md
│   ├── 资产/角色/<assetId>.md
│   ├── 资产/场景/<assetId>.md
│   ├── 资产/道具/<assetId>.md
│   ├── 分镜图/<shotId>.md
│   ├── 视频/<shotId>.md
│   └── 成片/成片.md
├── inputs/
├── assets/
├── storyboards/
├── clips/
└── final.mp4
```

### 4.2 Frontmatter

所有由 App 管理的页面使用最小 Frontmatter：

```md
---
projectId: project-a91f
entityType: shot
entityId: shot-03
status: confirmed
managedBy: short-video-factory
updatedAt: 2026-07-31T12:00:00+08:00
---
```

`status` 至少支持 `draft`、`confirmed`、`generating`、`generated`、`failed`；Frontmatter 只放机器需要稳定读取的字段，正文保留完整创作语义。

### 4.3 分镜 Markdown

单镜文件必须能被用户完整阅读，也能被 App 稳定提取：

```md
# 镜头 03

- 播放时长：3.5 秒
- 生成时长：4 秒
- 角色：[[资产/角色/小红]]
- 场景：[[资产/场景/办公室]]
- 道具：[[资产/道具/手机]]
- 景别：近景
- 机位：略低机位
- 运镜：缓慢推近

## 对应台词

...

## 画面提示词

...

## 视频提示词

...

## 生成结果

- 分镜图：`../../storyboards/003.png`
- 视频：`../../clips/003.mp4`
```

固定字段由标题和字段标签识别，不依赖字段顺序；缺失或冲突时，App 返回明确校验错误，不猜测、不静默生成。

### 4.4 资产 Markdown

资产页面保存身份特征、统一风格要求、用户原图、派生图和采用版本：

```md
---
projectId: project-a91f
entityType: asset
entityId: character-xiaohong
assetRole: character
status: confirmed
managedBy: short-video-factory
---

# 小红

## 身份特征

- 短发
- 绿色夹克

## 资产生成提示词

...

## 参考图

- 用户原图：`../../../inputs/xiaohong.png`
- 风格统一图：`../../../assets/角色/character-xiaohong/v2.png`
- 当前采用版本：`v2`

## 被引用的镜头

- [[分镜/镜头/shot-03]]
```

用户原图永不覆盖。2D 转 3D 或其他风格统一结果作为派生版本保存，只有用户确认后才标记为当前采用版本。

## 5. 模型工具合同

### 5.1 工具列表

第一版只开放当前项目所需的最小工具：

| 工具 | 作用 | 是否需要审批 |
| --- | --- | --- |
| `read` | 读取指定项目内 Markdown | 否 |
| `grep` | 搜索项目内 Markdown 内容和双链 | 否 |
| `write` | 创建或完整写入 Markdown | 是 |
| `edit` | 按版本修改 Markdown | 是 |
| `list` | 列出项目 Wiki 路径 | 否 |

工具必须拒绝绝对路径、`..` 穿越、项目目录外路径和未登记媒体目录。写入失败必须把真实错误返回模型。

### 5.2 模型行为

模型可以：

- 在生成分镜前读取确认文稿、视觉风格和已有资产；
- 在发现新主体后创建或更新资产 Markdown；
- 读取用户已上传的资产页面并绑定当前采用版本；
- 根据用户修改意见只编辑受影响的 Markdown 文件；
- 在最终回复中引用真实写入的文件路径。

模型不能：

- 声称写入了未实际写入的文件；
- 自己伪造图片、视频、音频路径；
- 绕过 App 直接执行付费媒体请求；
- 将工具调用过程、错误堆栈或临时内容写入 Raw。

### 5.3 执行边界

模型写完 Markdown 后，App 重新读取文件并校验：

1. 项目 ID、实体 ID 和路径一致；
2. 双链目标存在或被明确标记为待补齐；
3. 镜头时长、生成时长和提示词满足媒体合同；
4. 必需资产均有当前采用版本；
5. 只有校验通过的镜头才进入付费生成队列。

校验失败时不自动修正文稿，不再次要求模型输出 JSON，而是把具体文件、字段和错误交给模型或用户处理。

## 6. 界面合同

### 6.1 阅读/编辑

- 阅读模式：安全渲染标题、列表、表格、引用、代码、图片、普通链接和双链；
- 编辑模式：显示原始 Markdown，支持语法高亮和保存；
- 保存成功后重新读取文件并切回阅读模式；
- 保存冲突时保留用户草稿，要求用户选择，不静默覆盖；
- 复制操作复制原始 Markdown，而不是复制渲染后的纯文本。

### 6.2 三栏映射

- 左栏：项目、Raw、创作参数和当前阶段；
- 中栏：当前 Wiki Markdown 阅读/编辑页面；
- 右栏：AI 修改、生成和审批操作；
- 分镜页面支持目录式镜头切换，单镜 Markdown 独立编辑；
- 资产页面显示正向双链和反向引用，并显示原图、派生图、当前采用版本。

任何“阅读”“编辑”“双链跳转”都不得自动提交付费任务。

## 7. 媒体执行链

```text
模型写入分镜/镜头/*.md
  -> App 解析固定字段和双链
  -> 解析资产页面，得到当前采用参考图
  -> 用户确认或 App 按合同进入生成队列
  -> 生图模型接收画面提示词 + 绑定参考图
  -> 生视频模型接收视频提示词 + 分镜图
  -> 结果保存到受控媒体目录
  -> App 回写分镜图/*.md、视频/*.md、分镜/镜头/*.md
```

提示词仍以普通文本传给媒体模型。Markdown 只负责承载项目文档和参数；App 在内存中组装 API 请求，不把 Markdown 原文直接当作媒体 API 合同。

## 8. 迁移与实施顺序

### Task 0：冻结原应用边界

- 不修改、移动或批量复制 `jiucaihezi-app` 文件；
- 记录需要参考的文件、接口和测试；
- 短视频项目只在自身仓库实现适配。

### Task 1：统一 Markdown 渲染

- 在短视频 App 内建立安全 Markdown 渲染入口；
- 复用参考 App 的渲染语义和样式规则；
- 保留原文，不做破坏性清洗。

### Task 2：双链与反向链接

- 解析 `[[路径]]`、`[[路径|显示名]]`；
- 点击跳转目标 Markdown；
- 目标不存在时显示明确提示；
- 按需扫描当前项目生成反向引用。

### Task 3：Markdown 编辑保存

- 在现有文稿、分镜和资产页面加入阅读/编辑切换；
- 复用 `media-workspace.ts` 的原子写入和项目边界校验；
- 增加版本冲突保护和 Wiki 重建入口。

### Task 4：模型 Wiki 工具

- 将 `read`、`grep`、`list`、`write`、`edit` 作为当前项目受控工具；
- 模型自主决定读取和修改哪些 Wiki 文件；
- 工具真实结果和错误必须回传模型；
- 写入操作保留审批点。

### Task 5：媒体执行适配

- 从分镜 Markdown 解析提示词、时长和资产双链；
- 从资产 Markdown 解析当前采用参考图；
- 生成成功后回写媒体 Markdown；
- 保留 `state.json` 作为恢复和付费任务事实来源。

### Task 6：停止长 JSON 主合同

- 新工作流不再要求 Skill 输出完整 JSON；
- 保留旧 JSON 读取作为迁移兼容，不再扩大 JSON 合同；
- 新建项目默认直接使用 Wiki Markdown 工作流。

### Task 7：验收

- 创建两个项目并在项目选择器之间切换；
- 编辑并保存确认文稿、单镜分镜和资产页面；
- 从分镜跳转角色/场景/道具，再从资产反向跳回镜头；
- 只上传一个资产，确认缺失资产被明确标记并可补齐；
- 生成分镜图和视频后，重启 App 仍可从 Wiki 和状态恢复；
- 用 Obsidian/VS Code 打开项目目录，页面、双链和媒体相对路径可读。

## 9. 不做的事情

- 不修改 `jiucaihezi-app`；
- 不复制整个记忆工作台业务层；
- 不新增数据库、知识图谱服务或云端实时同步；
- 不在第一版实现块引用、嵌入、插件兼容和复杂协同编辑；
- 不让模型直接执行付费媒体 API；
- 不把工具事件、临时流式内容或模型内部思考写入 Wiki；
- 不因为 Markdown 可读就取消执行状态和媒体任务恢复机制。

## 10. 成功标准

一个新项目创建后，用户可以在 App 和外部 Markdown 软件中看到同一套项目资料：Raw、文稿、声音、分镜、资产提示词、参考图、分镜图、视频和成片。

用户可以直接编辑 Markdown；模型可以读取和修改当前项目 Wiki；双链可以在镜头与资产之间双向导航；媒体模型只接收提示词和参考图；应用重启后仍能从 Markdown 与 `state.json` 恢复；任何失败都有真实、可定位的文件或工具错误。
