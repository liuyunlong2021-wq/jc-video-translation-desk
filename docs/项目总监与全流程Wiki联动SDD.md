# 项目总监与全流程 Wiki 联动 SDD

> 日期：2026-08-03
> 状态：已实现，待全新项目人工验收
> 适用仓库：`/Users/by3/Documents/short-video-factory`
> 上位原则：一个项目、一套 Wiki、一套稳定实体 ID；结构化状态负责执行，Markdown 负责阅读、审阅和双链导航
> 相关 Skill：`skills/jc-film-style/SKILL.md`、`skills/jc-character-prompt/SKILL.md`、`skills/jc-scene-prompt/SKILL.md`、`skills/jc-prop-prompt/SKILL.md`、`skills/jc-script-storyboard/SKILL.md`
> 取代范围：取代旧文档中“角色、场景、道具分别从确认文稿自行识别资产”以及“分镜阶段重新选择导演”的流程；不改变已确认的资产图、视频、配音和成片执行合同

## 1. 一句话目标

在确认文稿与资产设计之间增加一个可见、可确认的“项目总监”环节：项目总监同时读取用户原始需求、确认文稿和项目参数，一次确定国别、时代、媒介、导演、视觉总纲及完整的角色/场景/道具清单，写入项目 Wiki；后续资产 Skill 只深化已确认实体，导演分镜只继承总监决策并专注逐镜编排。

## 2. 问题与根因

当前资产流程让三个 Skill 并行读取同一份确认文稿：

```text
确认文稿
  -> jc-character-prompt 自行判断有没有角色
  -> jc-scene-prompt 自行判断有没有场景
  -> jc-prop-prompt 自行判断有没有道具
```

这会产生四个问题：

1. 文稿生成时可能把原始需求中的画面主体压缩成旁白，资产 Skill 又只读确认文稿，导致主体角色丢失；
2. 三个 Skill 相互不知道对方识别了什么，没有统一的故事实体清单和完整性判断；
3. APP 允许任一 Skill 返回空数组，无法判断“角色为空”是合理无人画面还是识别遗漏；
4. 项目风格和导演决策散落在 UI 预设、资产 JSON 和导演分镜中，无法形成一个可追溯的项目级上游事实。

根因不是搜索或生图，而是确认文稿与专业资产设计之间缺少一个统一的项目级创意决策和实体注册环节。

## 3. 已确认产品决策

1. 项目内 `jc-film-style` 升级为“项目总监”Skill；保留目录名以减少迁移，产品显示名称改为“项目总监”。
2. 项目总监在用户确认文稿后、生成资产设计 JSON 前运行。
3. 项目总监必须同时读取用户原始需求和确认文稿；不能只读确认文稿。
4. 用户明确选择的比例、视觉风格、时长等项目参数是硬约束，总监不得擅自覆盖。
5. 项目总监负责“定国别、定时代、定媒介、定导演、定视觉总纲、定资产清单”，不负责生成角色、场景、道具的完整生图 JSON 或搜索词。
6. 角色、场景、道具 Skill 不再自行决定有哪些资产，只能逐项深化项目总监已经确认的资产。
7. 分镜 Skill 不再重新推荐或选择导演，必须继承项目总监确定的导演、参考作品和视觉总纲，只负责镜头、节奏、表演、声音和生图/视频提示词。
8. 项目总监结果同时保存为结构化执行状态和 `wiki/项目/项目总监.md`；二者来自同一次已校验结果。
9. 结构化状态、稳定 ID 和媒体路径仍是执行事实源；Markdown 是可读投影和双链导航，不能让自由文本代替状态合同。
10. 前端保持现有三栏，不增加第四栏。中栏新增“项目总监”内容视图，右栏提供生成、修改和确认动作。
11. 顶部既有制作阶段暂不增加第八阶段；项目总监是“文稿确认后、资产开始前”的强制闸门。
12. 所有付费图片和视频任务仍需用户主动触发；生成项目总监只调用文本 Skill，不得暗中搜索或生成媒体。
13. 产品尚未发布，不为旧测试项目增加兼容分支或迁移 UI；新项目按新流程验收。
14. 本期只建立可复盘证据链，不实现平台数据抓取、发布或自动市场复盘。

## 4. 新的唯一流程

```text
创建项目
  -> 输入需求或导入 Markdown，冻结 Raw 提交
  -> 生成、编辑并确认文稿
  -> 点击“生成项目总监方案”
  -> 项目总监读取 Raw + 确认文稿 + 项目参数
  -> 中栏展示并确认项目总监 Wiki
  -> APP 为确认的角色、场景、道具分配稳定资产 ID
  -> 三个专业资产 Skill 按总监清单逐项深化设计 JSON 和搜索词
  -> 搜索或上传参考图，生成并确认资产图
  -> 导演分镜继承项目总监方案并绑定稳定资产 ID
  -> 生成分镜图、视频、配音、字幕和成片
  -> 项目 Wiki 保留全流程文档与双链
```

项目总监未确认时，不允许生成资产设计 JSON；资产未完成时，继续遵守现有分镜闸门。

## 5. 项目总监 Skill 合同

### 5.1 应用运行模式

在 `skills/jc-film-style/SKILL.md` 增加单轮应用模式：

```text
mode: app-director
```

该模式不得启动原 Skill 的 A/B/C/D 多轮问答、Pinterest 搜索、浏览器操作或自行写文件。APP 负责输入、校验、持久化和 Wiki 写入。

输入：

```ts
interface ProjectDirectorInput {
  mode: 'app-director'
  rawRequest: string
  approvedScript: string
  project: {
    styleId: string
    visualStyle: string
    aspectRatio: '9:16' | '16:9'
    targetDuration: number
  }
}
```

输入规则：

- `rawRequest` 保存用户最初的创作目标、题材、人物和画面意图；
- `approvedScript` 保存最终确认的旁白、对白和叙事文本；
- 确认文稿没有重复某项原始画面要求，不代表该要求被删除；只有确认文稿明确与原始需求冲突时，才以用户最后确认的内容为准；
- 用户选择的视觉风格和比例必须原样进入总监结果。

### 5.2 输出合同

Skill 只返回一个 JSON 对象，不返回 Markdown、文件路径、图片、搜索结果或解释性前后缀：

```ts
type PlannedAssetRole = 'character' | 'scene' | 'prop'

interface ProjectDirectorDraft {
  project: {
    title: string
    format: string
    genre: string
    countryRegion: string
    era: string
    medium: string
    aspectRatio: '9:16' | '16:9'
    visualStyle: string
  }
  direction: {
    director: string
    referenceWork: string
    rationale: string
    visualAnchor: string
    colorLanguage: string
    cameraLanguage: string
  }
  assets: Array<{
    role: PlannedAssetRole
    label: string
    aliases: string[]
    description: string
    storyFunction: string
    identityTraits: string[]
    required: boolean
    evidence: string
  }>
  completeness: {
    narrativeSubjectRequired: boolean
    noCharacterReason: string
    warnings: string[]
  }
}

interface ProjectDirectorPlan extends Omit<ProjectDirectorDraft, 'assets'> {
  assets: Array<ProjectDirectorDraft['assets'][number] & {
    id: string
  }>
}
```

约束：

- Skill 不生成最终 `assetId`，稳定 ID 由 APP 在输出通过校验后分配；
- `evidence` 只写该实体来自原始需求或确认文稿的哪项事实，不复制整篇原文；
- “角色、场景、道具”作为产品功能名词时，不得直接当成三个剧情实体；
- 任何具名人物、说话者、动作执行者或需要跨镜保持一致的主体必须进入角色清单；
- 主要地点和需要保持空间连续的环境必须进入场景清单；
- 品牌设备、包装、APP 载体和跨镜使用的重要物件必须进入道具清单；
- 无角色项目可以返回空角色清单，但必须设置 `narrativeSubjectRequired: false` 并填写明确的 `noCharacterReason`；
- 项目存在行动主体时，不得用“旁白广告”作为角色为空的理由。

### 5.3 APP 校验与 ID 分配

APP 至少校验：

- 项目与导演字段非空；
- `aspectRatio` 与用户选择一致；
- `assets` 只包含三种合法类型；
- 每个实体的 `label`、`description`、`storyFunction`、`identityTraits` 和 `evidence` 完整；
- `narrativeSubjectRequired === true` 时至少存在一个必需角色；
- 角色为空时 `noCharacterReason` 必填；
- 同类型名称或别名不能互相冲突。

校验通过后，APP 为资产分配现有格式的稳定 ID：

```text
asset-character-xxxxxxxx
asset-scene-xxxxxxxx
asset-prop-xxxxxxxx
```

总监方案生成但尚未确认时是草稿，不写入正式资产注册表。用户确认后，APP 为每项资产补上稳定 `id`，形成 `ProjectDirectorPlan`；结构化方案和稳定 ID 一起进入项目状态并写入 Wiki。

## 6. 专业资产 Skill 的新边界

项目总监确认后，APP 按资产清单调用现有专业 Skill：

```text
character -> jc-character-prompt
scene     -> jc-scene-prompt
prop      -> jc-prop-prompt
```

优先复用三个 Skill 已存在的 `mode: "app-runtime"` 单资产深化合同。每次输入一个已分配 ID 的总监资产和项目风格，返回该资产的完整 `design` 与 `searchQuery`。

```ts
{
  mode: 'app-runtime',
  asset: directorAsset,
  projectStyle: confirmedDirectorPlan.project
}
```

强制规则：

- 专业 Skill 必须原样返回 `asset.id`；
- 不得新增、删除、合并、拆分或改名总监资产；
- 只深化本类型设计，不重新分析全篇文稿；
- 完整设计 JSON 仍是生图唯一提示词事实源；
- 搜索词继续从完整设计 JSON 派生；
- 单项失败只标记该资产失败，不丢弃其他已成功资产。

因此原有三个 `app-plan` 并行“各自识别 + 各自设计”的入口退出 APP 主流程；交互式 Skill 能力可以保留，不参与产品编排。

## 7. 分镜 Skill 的继承合同

`jc-script-storyboard` 的应用输入增加已确认的项目总监方案或其受控 Wiki 路径：

```text
wiki/项目/项目总监.md
```

分镜 Skill 必须继承：

- 导演与参考作品；
- 国别、时代和媒介；
- 视觉锚点、色彩语言和镜头语言；
- 已确认的角色、场景、道具稳定 ID。

分镜 Skill 不再：

- 推荐三个导演供选择；
- 用新的导演覆盖项目总监；
- 创建、删除或修改资产；
- 把资产显示名称当成稳定 ID。

分镜阶段只决定逐镜景别、机位、动作、表演、声音、时长、资产引用以及分镜生图和视频提示词。Veo 与 Grok 的执行路线继续由现有视频模型选择自动决定。

已确认 `projectDirectorPlan.assets` 是项目资产的唯一合法名单，其中的 `entityId` 等同资产身份证。分镜只能绑定名单内 ID；模型写出的桌灯、家具、路人或其他无 ID 内容仍可作为普通画面描述，但不得成为资产、不得绑定参考图、不得进入资产区。APP 对名单外链接做内部归一化并忽略该绑定，不向用户报「未知资产 ID」错误。若剧情确实需要新的跨镜重要资产，必须回到项目总监修改清单，不允许分镜自动升格。

## 8. 项目 Wiki 结构与双链

### 8.1 新增路径

项目固定骨架增加：

```text
wiki/
├── 项目/
│   └── 项目总监.md
├── 文稿/
│   └── 确认文稿.md
├── 资产/
│   ├── 角色/
│   ├── 场景/
│   └── 道具/
├── 分镜/
│   ├── 导演总览.md
│   └── 镜头/
├── 声音/
├── 分镜图/
├── 视频/
├── 字幕/
└── 成片/
```

不预先生成空的 `项目总监.md`；只有总监方案确认成功后才写入正式页面。确认时同步为清单内每个实体创建一份包含总监事实和 `planned` 状态的最小资产页面，避免项目总监产生断链；专业资产 Skill 深化成功后原位补全同一页面，不创建第二个实体。

### 8.2 项目总监页面

`wiki/项目/项目总监.md` 至少展示：

```md
# 项目总监

- 来源：[[文稿/确认文稿]]
- 国别与时代：韩国，当代
- 媒介与比例：韩漫，9:16
- 导演与参考作品：……

## 视觉总纲

……

## 角色

- [[资产/角色/asset-character-xxxx|创作者]]：……

## 场景

- [[资产/场景/asset-scene-xxxx|创作工作室]]：……

## 道具

- [[资产/道具/asset-prop-xxxx|点一点工作平板]]：……

## 完整性检查

- 行动主体：已覆盖
- 主要场景：已覆盖
- 跨镜重要道具：已覆盖
```

页面使用普通 Markdown 和相对 Wiki 链接，不复制完整资产设计 JSON。

### 8.3 正向链接和反向引用

关系固定为：

```text
Raw 提交
  -> 确认文稿
  -> 项目总监
  -> 角色 / 场景 / 道具
  -> 导演总览
  -> 单镜分镜
  -> 分镜图 / 视频 / 声音 / 字幕
  -> 成片
```

- 项目总监正向链接确认文稿和全部确认资产；
- 每个资产页面链接回项目总监，并继续展示引用它的镜头；
- 导演总览链接项目总监、确认文稿和已绑定资产；
- 单镜、分镜图和视频沿用稳定 `shotId` 和资产 ID；
- 成片页链接所用导演总览、字幕和最终媒体；
- `wiki/来源索引.md` 增加项目总监的 Raw、确认文稿和 Skill 来源；
- 反向引用继续由应用根据正向关系计算，不在两端重复保存第二套关系数据。

### 8.4 执行状态与 Markdown

结构化状态新增已确认的 `projectDirectorPlan`，它是 APP 继续执行、校验和失效的来源。`项目总监.md` 是同一数据的可读投影。

项目加载、分镜 Wiki 回读和状态重建都必须用 `projectDirectorPlan.assets[].id` 过滤资产及镜头引用。历史测试或旧流程留下的其他资产 Markdown 不能因为仍存在于 `wiki/资产/` 就恢复成有效资产。项目总监清单的顺序同时是状态中的资产顺序。

本期中栏允许查看总监 Markdown，并通过右栏 AI 修改入口生成结构化修订。未确认草稿只在内存中用现有 Markdown 阅读组件渲染，不占用正式 `wiki/项目/项目总监.md`；确认成功后再写入正式 Wiki。不支持用户在外部编辑器直接修改 Markdown 后自动反向改写状态，该能力没有必要为本期增加双向同步复杂度。

## 9. 前端 UI 方案

### 9.1 总体原则

- 保持现有三栏：左栏导航，中栏内容，右栏当前对象操作；
- 不增加第四栏，不增加弹窗式确认流程，不建立第二套项目页面；
- 项目总监是明确可见的制作闸门，但暂不增加顶部第八阶段；
- 中栏只展示内容，生成、修改和确认按钮继续放在右栏。

### 9.2 文稿确认后的状态

用户确认文稿后：

1. 左栏在“文稿”和“资产”之间显示固定入口“项目总监”；
2. APP 自动选中“项目总监”视图；
3. 中栏显示简洁空状态“尚未生成项目总监方案”；
4. 右栏显示唯一主操作按钮 `生成项目总监方案`；
5. “生成资产设计 JSON”保持可见但禁用，禁用原因显示“请先确认项目总监方案”。

按钮必须直接触发一次文本 Skill，不再弹出二次确认框。

### 9.3 生成后的中栏

中栏使用现有 Markdown 阅读器展示 `wiki/项目/项目总监.md` 的草稿投影，内容顺序固定：

```text
项目定位
导演与参考作品
视觉总纲
角色清单
场景清单
道具清单
完整性检查
```

角色、场景、道具条目使用现有资产状态和图标语言，不在总监页加入参考图上传、搜索或生图按钮；这些操作仍只属于资产页。

### 9.4 右栏操作

草稿生成后，右栏提供：

- 主按钮：`确认项目总监方案`；
- 次按钮：使用现有重新生成图标与 Tooltip，重新生成草稿；
- 现有 AI 修改文本框：用户可输入“增加一个创作者角色”“把国别改成韩国”等意见，修改后重新校验完整合同。

确认后：

- 中栏保留总监文档；
- 主按钮切换为 `生成资产设计 JSON`；
- 用户仍可从左栏回到项目总监查看；
- 已生成下游内容后修改总监方案，必须明确提示将失效资产设计及后续结果，再按现有失效机制执行，不保留并行旧状态。

不增加角色/场景/道具数量统计卡、独立关系图、版本对比器或市场分析面板。本期已有 Markdown 和资产列表足以完成审阅。

### 9.5 顶部步骤与完成状态

顶部继续使用现有制作阶段。项目总监的状态反映在“文稿到资产”的过渡中：

```text
文稿已确认，总监未生成   -> 项目总监入口待处理
总监草稿已生成           -> 项目总监入口处理中
总监已确认               -> 项目总监入口显示完成对号，资产操作解锁
```

资产阶段的完成条件仍是所有必需资产拥有已生成资产图；项目总监确认不能冒充资产完成。

## 10. 状态、持久化与失效

结构化状态增加最小字段：

```ts
projectDirectorDraft: ProjectDirectorPlan | null
projectDirectorPlan: ProjectDirectorPlan | null
projectDirectorStatus: 'empty' | 'draft' | 'confirmed'
```

如果现有 Store 可以从两个对象是否存在推导状态，则不额外持久化 `projectDirectorStatus`，避免重复状态。

失效规则：

| 上游变化 | 必须失效 | 保留 |
| --- | --- | --- |
| 原始需求重新提交或确认文稿修改 | 项目总监、资产、分镜、媒体、配音、成片 | 项目与 Raw 历史 |
| 比例或视觉风格修改 | 项目总监、资产、分镜、媒体、成片 | 确认文稿 |
| 项目总监草稿修改但未确认 | 仅草稿 | 已确认方案和下游结果 |
| 已确认项目总监方案被替换 | 资产设计及全部下游结果 | 确认文稿与 Raw |
| 单个资产设计修改 | 沿用现有精确下游失效 | 项目总监清单和其他资产 |

保存项目和重开 APP 后，项目总监草稿、已确认方案、Wiki 页面、稳定资产 ID 和当前视图都必须恢复到同一项目，不能跨项目串入。

## 11. 错误处理

- Skill 输出格式错误：保留当前确认文稿，显示合同错误，不创建半份总监 Wiki；
- 完整性检查失败：中栏可展示草稿，但确认按钮禁用并明确指出缺失角色、场景或道具；
- 总监 Wiki 写入失败：不得把结构化方案标记为已确认；
- 某个资产深化失败：保留总监方案和其他成功资产，只重试失败项；
- 分镜尝试覆盖导演：拒绝整次分镜更新，保留上一次有效分镜；分镜写出名单外资产链接时，APP 只移除该绑定并继续，不将它恢复为资产，不向用户显示未知 ID 错误；
- 用户取消总监生成：停止本地等待，不写草稿，不影响确认文稿。

## 12. 市场复盘扩展边界

本期 Wiki 必须保证以后可以沿以下路径追溯：

```text
成片版本
  -> 字幕 / 声音 / 最终时间轴
  -> 单镜视频与分镜提示词
  -> 角色 / 场景 / 道具
  -> 项目总监
  -> 确认文稿与 Raw
```

未来可以增加：

```text
wiki/复盘/<日期>-<平台>-<成片版本>.md
```

用于记录播放、完播、互动、转化、评论和逐时段留存，并链接对应成片与镜头。复盘只能提出有证据的判断和下一轮建议，不得把相关性表述成确定因果，也不得直接覆盖当时的原始制作文档。

本期不实现平台登录、自动抓数、发布、数据看板或自动改稿；只保证现有 Wiki 文档和稳定 ID 足以承接后续复盘。

## 14. 最小测试集

### 14.1 合同测试

1. 原始需求明确“一个创作者完成制作”，确认文稿压缩成旁白时，总监仍必须输出创作者角色；
2. 纯风景、无人物需求允许角色为空，但必须输出 `noCharacterReason`；
3. 总监输出行动主体必需但角色为空时，解析器拒绝确认；
4. 比例和视觉风格必须与用户项目参数一致；
5. APP 分配稳定 ID，专业资产 Skill 不能更改 ID 或增加清单外资产；
6. 分镜输出的导演必须等于总监方案；分镜中的名单外资产链接被静默移除，不增加资产数量。

### 14.2 Wiki 测试

1. 确认总监方案后生成 `wiki/项目/项目总监.md`；
2. 项目总监页链接确认文稿和全部资产，所有资产链接在确认后立即有对应 `planned` 页面；
3. 资产页与导演总览可以回到项目总监；
4. `wiki/index.md` 和来源索引包含项目总监入口；
5. 重建 Wiki 不改变稳定 ID，不丢总监页面。
6. `wiki/资产/` 中即使残留名单外的历史 Markdown，项目加载和转分镜后的有效资产仍严格等于项目总监清单。

### 14.3 UI 测试

1. 确认文稿后自动进入项目总监视图；

3. 项目总监未确认时资产按钮可见但禁用，并显示正确原因；
4. 确认后资产按钮立即解锁；
5. 切换项目或重开 APP 后恢复正确总监页面和状态；
6. 中栏只展示总监内容，所有操作只在右栏；
7. 桌面和窄窗口下文字、按钮和 Markdown 不溢出。

### 14.4 完整流程验收

使用一个 30 秒、9:16、韩漫风格的“创作者使用点一点完成短视频”的小剧情，从新建项目走通：

```text
确认文稿
  -> 项目总监识别创作者、工作室和点一点设备
  -> 确认总监 Wiki
  -> 深化并生成三类资产
  -> 分镜继承总监导演和资产 ID
  -> 生成分镜图、视频和成片
  -> 检查 Wiki 可以从成片逐层回到 Raw
```

验收重点不是图片是否漂亮，而是主体不丢失、实体不重复、导演不漂移、链接不断裂、项目重开可恢复。
